v181 매물별 개인 첨부자료 (2026-11-11)

사용자 요청
- 임대인에게 받은 매매표·임대현황표를 해당 매물에서 보관/열람한다.
- 목록 메모 옆 첨부 버튼: 파일이 있으면 빨간색(#dc2626)과 개수, 없으면 중립색.
- 첨부창에서 파일별 올린 날짜/시각(KST), 이름, 크기, 보기/다운로드를 제공한다.
- v180 층·호실 현황의 연한 초록색 강조는 별개이며 그대로 유지한다.

저장·보존 경계
- R2 MEDIA의 비공개 바이트 + 기존 D1 cloud_state/listingAttachmentsV181 메타데이터. 새 DB migration이나 공개 URL 없음.
- 정규 로그인 계정과 정확한 내부 원장 ID에 귀속. 원본 광고/주소/현재 대표 광고에 붙이지 않는다.
- 다른 계정은 목록 개수·파일명·본문 모두 읽을 수 없다. 일반 cloud_state API로 이 scope를 변경할 수도 없다.
- 대표 광고가 바뀌어도 같은 원장에 유지한다. 명시적 원장 병합은 기존 원자 DB batch에서 모든 소유자의 메타데이터만 새 원장으로 옮기며 날짜/파일/휴지통 상태를 보존한다.
- 사진/PDF는 별도 보기, 엑셀은 다운로드. JPG/PNG/WebP/PDF/XLS/XLSX, 파일당20MiB, 원장당100개/250MiB, 계정당1000개/1GiB(휴지통 포함).
- 파일 서명·형식 검사, 불변 UUID+hash 영수증, 중복 요청1회 저장, 파일 선택창/비동기 응답의 계정·원장 경계, CAS 삭제/복원.
- 삭제는 휴지통이며 영구삭제 UI 없음. 원본 bytes와 업로드 날짜를 유지한다. 총 용량은 휴지통을 포함하므로 삭제만으로 한도가 해제되지는 않는다.
- DB 결과가 완전히 유실되면 확정 여부를 읽어 대조하고 미확정 bytes를 무조건 삭제하지 않는다. 극단적인 저장소 장애의 orphan은 별도 감사 대상으로 남을 수 있다.

목록·사진 원칙
- 기존 목록/사진/메모/가격 쓰기 경로와 광고 photoCount를 변경하지 않는다.
- 현재 렌더된 카드에 한해24개씩 작은 첨부 개수 GET, 150ms 지연 묶음, 메모리 최대500개. 전체 원장 조회/파일 바이트 선다운로드/정기 폴링 없음.
- 첨부 UI 모듈은 클릭 때만 fingerprint URL로 로드한다. 목록 표시가 첨부 응답을 기다리지 않는다.
- 이미 준비된 카드/클러스터250ms·실제 사진500ms 회귀 상한을 유지한다. 최초 방문 기본 자료 준비 약3.2초의 기존 미달을 해결했다고 보고하지 않는다.

검수
- 가상 SQLite/R2+실제 인증 Worker 경로에서 파일 bytes 저장/조회, 계정 격리, 정확 원장, 동일 UUID 동시 요청, 휴지통/복원, 저장 실패/용량, 형식, 원장 병합을 검사한다.
- PC/휴대폰14사례: 빨간 버튼/날짜/실제PNG decode, 새로고침 보존, 늦은 개수 응답, 응답 유실, 계정/다른 원장 전환, native 선택창 A→B 보호, 가로/세로, Back/Escape, 대표 광고 교체.
- 첨부 버튼 추가가 휴대폰 매매 수정 버튼을 숨기던 중간 오류를 임대 카드 범위 CSS로 좁혀 수정했다. 첨부14+매매수정8=22개 재검수 통과.
- unified 직접 fetch는 기존 접근 경계 검사가 차단해 공용 data-access로 옮겼다. 기존 검사를 완화하지 않았다.
- index.html/js/script.js의 기존 혼합 줄끝은 원래 byte를 유지했다. 전체 CRLF 변환을 취소했고 CSV 파서 검사는 기존대로 통과한다.
- 운영 매물에 검수용 파일 업로드나 메모/조건 변경을 하지 않는다. 배포 후 읽기 전용 연결/화면과 양 도메인 자산을 검수한다.
