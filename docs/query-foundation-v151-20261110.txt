준비한 코드
- tools/build-query-runtime-v151.mjs: 실제 브라우저의 가격·층·출처·매매·정렬·필지 함수를
  빌드 시 정적 ES 모듈로 추출. Worker 런타임 eval 없음. 생성 파일은 git/lint 제외.
- query-stream-v151.js: UTF8 JSON을 원장 그룹 단위로 읽고 큰 사진 주소 목록은 조회 계산에서
  분리. 원문/운영 데이터 삭제 아님. 잘림/중복 키/잘못된 부모/크기·깊이 초과 거부.
- query-engine-v151.js: 최대128원장씩 투영하고 전체 결과의 대표 병합·정렬은 마지막에 수행.
  명시한 원장 proof가 맞지 않으면 부분 결과를 전체 결과처럼 반환하지 않는다.
- query-worker-v151.js: R2의 검증된 CSV·원본과 정확 ID의 listingOriginals 보완을 이용하는
  비공개 읽기 조회 초안. 조회용 준비 캐시만 별도 R2 키 사용, 운영 매물 쓰기 없음.
  일반 기본 조회가 동일 revision으로 준비되면 SQL/큰 파일 없이 2개 R2 읽기로 반환하는
  단위 검증. 공개 인증/서비스 연결은 아직 없다.
- 브라우저 전달 형식은 읽기 전용 지도·목록 식별 행이다. 수정 가능한 원장을 흉내 내지
  않는다. 실제 카드/저장은 별도 정확 ID 조회와 원장/원본 proof 검증이 필요하다.

확인한 한계와 실험
- 전체 61,480광고를 한 번에 메모리에 펼치는 방식은 Node heap128MB에서 실패하여 채택 안 함.
- Object의 중간 필드 delete는 V8 사전 객체로 바뀌어 메모리 사용을 키웠다. 사진 경로는
  조회 객체에서 undefined로 놓고, 전체 광고 객체를 보유하는 대신 제한된 배치로 계산한다.
- 다른 시각의 읽기 전용 백업 CSV/원본은123원장이 proof 불일치했다. 성능 샘플에서만 이를
  명시적으로 제외한18,485원장으로 측정했다. 운영 데이터를123개 제외한 것이 아니다.
  제품 경로는 이를 조용히 제외하지 않고 정확 ID 조회로 보완하거나 실패한다.
- 이 샘플은 전역/미좌표 포함13,275행이며 운영 지도 활성 총건수가 아니다.
  Node heap128MB에서 배치/직렬화 완료, 약74MB heap. 전달 JSON4.58MB/gzip1.21MB,
  로컬 동시 검수 중 약9초. 이 수치는 웹 첫 카드/Workerd 메모리/낮 수집 중 속도 증거가 아니다.
- 단위16개: 수동 월세·지하층, 누락/0, 지번/찜/범위, 완료/후보, 잘못된 proof,
  배치/일괄 결과 일치, 그룹이 배치를 가로지르는 대표 선택·220만원, 응답 경합/누락 거부,
  KST 날짜, 읽기 전용 전송, 기록 범위 한도, 준비 캐시의 큰 파일/SQL 미사용.
- pnpm run cf:query:check는 생성+비공개 Worker dry-run만 한다. 서비스 배포 명령이 아니다.
  번들823.12KiB/gzip189.06KiB. 공개 앱과의 실기 검증은 이번 기반으로 하지 않았다.

완료 전 필수로 남은 일
1. 공개 인증 경계 안에서만 비공개 조회를 연결하고 실제 Workerd128MB/수집 중 경합을 검증.
   공개된 페이지/조회 결과의 revision과 원장별 proof를 끝까지 유지해야 한다.
2. 브라우저를 전체 CSV/사진 목록 선다운로드에서 읽기 전용 목록/지도 식별 자료와
   실제 보이는 카드/상세의 정확 ID 조회로 옮긴다. 기존 allItems가 완성 원장 전체라는
   가정이 많은 점을 먼저 감사해야 한다. 식별 행을 수정/인쇄/찜/연락처용 완성 자료로
   쓰거나 부분 캐시를 전체 캐시로 저장하지 않는다. 대량 선택/다른 시장/오늘 범위도 보호.
3. 별도 계정·쿼리·세대 캐시와 확정 저장 patch/다른 탭 경합/메모 focus/사진 DOM 보존.
   수집 중 D1과 게시된 스냅샷이 다를 때 이전 조건을 최신으로 가장하는 우회 금지.
4. PC·폰 원칙 검사에 새 조회 모드를 추가, 기존 검사와 모두 통과 후 실제 Edge/웹에서
   콜드·재방문·새로고침·지도 이동·상세1→2·수정/보존/다른 원장 보호를 검증.
5. 백업을 유지하고 배포한 뒤 cf:verify 및 실제 새 코드 적용 확인. 성공 배포 기록만으로
   적용됐다고 하지 않는다. 목표가 남아 있으면 완료라고 말하지 않는다.
