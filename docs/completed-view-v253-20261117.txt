원인
열린 운영 웹에서 완료만 보기를 누른 요청을 private Worker tail로 대조했다.
원본 proof가 바뀐 626개를 순차 조회하는 repairs 단계가 37,038ms까지 걸렸으며,
전체 요청은 wall 53,965ms / CPU 15,043ms 뒤 취소됐다. 재시도에서도 같은 대조를 반복했다.
기본 active 전용 준비 catalog로 완료 광고를 대신할 수 없으므로 단순 필터 무시나
오래된 active 목록 유지로 통과시키지 않는다. 실제 후보 광고/수동 계약완료가 함께 존재한다.

보완
1. all/completed 별도 완전 광고별 catalog와 공통 정렬별 압축 결과를 private R2에 보관.
   계정 인증과 최종 revision, 원장/광고 proof, market, availabilityView 확인을 유지한다.
   다른 view 자료를 active/완료 전체로 바꿔 부르지 않는다. 관리메모/전화 신규 wire 노출 없음.
2. 변경 50개 이하에는 기존 정확 ID 대조 patch를 재사용, 더 많으면 검증 전체 준비.
   기존 warm pass 한 번에 stale view 하나만 준비. 수집/예약 시작·중단·시간 변경 없음.
3. 완료된 압축 bytes만 최대 8MB/8개 메모리 보관. 진행 중 I/O promise 전역 보관 없음.
   다른 조건 결과는 4개 bounded slot + 전체 조건 hash, 공통 정렬은 고정 key.
4. 전체 준비 원본 대조는 최대 4개(각 50 ID) 독립 읽기 병렬화 후 원래 순서로 처리.
   누락/proof/다른 ID 검사는 유지. 무제한 동시 조회·불완전 결과 저장 없음.
5. 수동 계약완료와 수집 누락 후보의 서로 다른 대표 선택/개수/사진 처리 유지.
   기본 active 조회 및 사용자 메모·조건·원장 데이터는 변경하지 않는다.
