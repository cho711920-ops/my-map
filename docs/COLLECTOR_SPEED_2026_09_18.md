## 근거와 한계

- 9월 18일 오전 11시 시작 실행에서 네이버 중구 완료(11:13:58) 뒤 동구 시작(11:39:13) 사이 긴 간격이 있었고, 서구는 재시도 대기로 보고됐다. 이 시간 전체를 특정 요청의 처리 시간이라고 단정하지 않는다.
- 네이버·당근의 무제한 응답 대기, 당근의 불필요한 결과 재조회, 경과 시간 정규식 문제는 코드와 격리 회귀검사로 확인했다.
- 백그라운드 타이머 제한은 [Chromium 설명](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)과 [Google Chrome 실행 옵션 문서](https://github.com/GoogleChrome/chrome-launcher/blob/main/docs/chrome-flags-for-tools.md)에 근거한 지연 가능성이다. 이번 운영 수집의 모든 정체가 이 원인이라고 확정하지 않는다.
- 속도 개선은 응답 대기·중복 조회·불필요한 재시도를 줄이는 방식이다. 공급처 호출 수를 무리하게 늘리거나 정확한 전체 목록 확인을 생략하지 않는다.
- 전체 운영 수집의 단축 시간이나 배수는 다음 새 버전 실행 완료 후에만 비교할 수 있다. 로컬 검사 시간은 실수집 속도 측정값이 아니다.

## 검증·반영 기록

- 전체 회귀검사 826/826 통과. 정상 응답, 응답·본문 정체, 잘못된 JSON, 저장 여부 불확실, 도시 전체 수집 중단 경계, 오래된 화면 조회 중단, 경과 시간만 바뀌는 정체, 정상 탭 오인 재시작 방지를 포함한다.
- ESLint, 부분 strict 타입 검사, 정적 자산 빌드, Worker 배포 dry-run, 런처 PowerShell 구문검사 통과. 런처 구문검사에서 실제 런처를 실행하지 않았다.
- 테스트의 공급처·시간·저장 응답은 격리된 대역이다. 변경 효과를 측정하려고 운영 수집을 별도로 시작하지 않는다.
- 현재 실행 종료 후 기존 설치 코드만 별도 백업하고 설치 코드를 갱신한다. 브라우저 프로필·로그인·대상·예약은 보존하며 새 런처 옵션은 다음 예약 시작 시 적용된다.
