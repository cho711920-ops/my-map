- 사용자가 목록 드래그 시 위로 튕기는 느낌·매끄럽지 않음을 제보하고 검수를 요청했다.
- 추가 답변: 'PC에서 휠·스크롤바로 이동할 때'. PC를 우선 확인했다.
- 운영 페이지/데이터/수집 브라우저를 조작하지 않고, 실제 목록 UI/가상화 코드와
  로컬240건 검사 자료를 사용하는 격리 Edge 브라우저에서 실측했다.
- PC1280×800, 목록 높이740px. 외부 공급처·지도 SDK 통신 차단, 운영 저장 없음.
- 검수 단계이며 제품 코드 수정·배포는 하지 않았다. 현재 웹 배포는 이전 월세 수정 버전이다.

실측 결과
1. 스크롤바 범위가 한 번에 커지는 문제
   - 최초18장만 DOM에 있고 하단 미표시 매물의 공간이 없는 구조다.
   - 18장이 추가되면서 scrollHeight가2310→4560px로 바뀌었다. 이후6810·9060px로 계속 증가.
   - 실제15px 폭 네이티브 스크롤바 드래그24회에서 같은13px 마우스 이동에 대해
     목록 이동량이41~43px였다가, 카드 추가 다음 입력은0px, 이후83~85px로 달라졌다.
   - scrollTop 자체는 감소하지 않았다. 손잡이 위치/크기는 전체 길이 비율이 바뀌어 위로 변한다.
     예: scrollTop724에서 비율상 손잡이 시작은 약232→118px(트랙 단순 비율 계산).
     이것은 실제 매물 내용의 위 방향 역주행과 구분한다.
2. 카드 교체 시 프레임 지연 가능성
   - 아래쪽 추가 배치21.4/37.0/26.1ms, 위쪽 복원26.1/26.8ms 관찰.
   - 같은 목록 showList 재생성5회39.6~41.7ms. 주변 PC 부하에 따라 달라지는 실측값이다.
   - 60Hz 한 프레임16.7ms보다 길어 배치 경계에서 순간 끊김이 생길 수 있다.
   - 제거 루프에서 카드 높이 읽기와 DOM 제거를 번갈아 수행하고,
     showList는 동일 목록도 기본적으로 지운 뒤 다시 만드는 부분을 개선 후보로 확인했다.
3. 재현하지 못한 현상
   - 휠 아래24·위24회에서 입력 반대 방향 scrollTop 이동0회.
   - 동일 목록 재렌더링5회에서 기준 카드 위치 변화0px.
   - 실제 운영에서 사진·원본정보가 바뀌는 도중의 경쟁 조건과 사용자 PC의 모든 부하는
     전수 재현하지 않았다. '튕김이 전혀 없다' 또는 '원인을 모두 확인했다'고 표현하지 않는다.

권장 수정 방향 (미구현)
- 전체 목록의 상·하단 가상 공간을 유지해 전체 스크롤 범위를 안정화하고 보이는 카드만 교체.
  가변 카드 높이·열린 메모·목록 추가/삭제에도 현재 보는 기준 카드가 움직이지 않게 검증할 것.
- 카드 높이 측정을 먼저 모은 뒤 일괄 제거하고, 조건/내용이 같으면 불필요한 전체 DOM 교체 감소.
- 자동 원본정보 갱신과 스크롤이 겹칠 때도 최신 필터 조건과 현재 보는 매물 위치를 함께 유지.
  최근 월세 투영 수정의 필터 재검사를 생략하거나 원본 사진·개수 갱신을 늦추는 방식은 피한다.
