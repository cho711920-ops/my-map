JS부동산 조회 분리 운영 적용 v152–v154 / 2026-11-10

작업 범위
기존 v151의 초안을 실제 인증·목록·지도·상세·찜·수정 흐름에 연결했다.
전체 CSV와 전체 원본/사진 목록을 받아야 첫 화면이 뜨던 의존성을 제거했다.
기존 가격·원본 선택·층수·수익률 규칙을 빌드 때 정적으로 추출해 서버에서도 사용한다.
별도의 가격 판정 규칙이나 주소 기반 원장 합치기를 만들지 않았다.

구조
- 공개 js-map Worker의 인증/기대 계정 검증 안에서 listingQuery를 제공한다.
- LISTING_QUERY 서비스 바인딩은 비공개 js-map-query-v151로 연결된다.
  이 서비스는 public route, workers.dev, preview URL을 만들지 않는다.
- 읽기용 목록은 ID·좌표·표시 조건·부모 검증값만 전달한다. 메모·전화·전체 사진·쓰기용 원장은 전달하지 않는다.
- allItems에는 정확-ID 조회로 검증한 실제 원장만 둔다. 지도용 행은 별도 읽기 전용 레지스트리다.
- 실제 카드/상세/수정/인쇄/대량 선택에는 필요한 원장을 50개 이하 묶음으로 조회한다.
  선택/찜의 알려지지 않은 원장도 같은 경로로 확인한다. 주소/행번호로 쓰기 대상을 대체하지 않는다.
- 지도 이동·정렬·정확 지번 검색은 확보한 인덱스와 기존 공통 규칙을 재사용한다.
- 기본 조회는 R2의 준비된 화면으로 응답한다. 원본 메타데이터는 사진 목록 없이 별도 준비한다.
  건물/토지용 메타데이터는 임대 원장을 제외한다. 전체 광고를 한 번에 메모리 객체로 펼치지 않고 512원장씩 처리한다.
- 수집 중 메타데이터 준비의 전체 epoch가 바뀌더라도 각 원장/원본 부모 검증과 변경 이력으로 확인한다.
  전체 수집이 완료됐다는 뜻이 아니다. 누락 이력·1024건 초과·부모 불일치는 최신 목록으로 인증하지 않는다.
- 수동 저장 후 기존 기본 화면의 변경 ID가 50개 이하이면 그 ID만 서버 점조회해 화면을 보완한다.
  새 원장/이력 불완전/범위 밖 변경은 전체 검증된 메타데이터를 통해 준비한다.
- 사용자 조건 조회 캐시는 시장마다 4슬롯, 프로세스 캐시는 4MB/8개로 제한한다.

새로고침과 저장
- IndexedDB js-query-scopes-v152/views: 계정·시장별 기본 슬롯과 필터 슬롯을 분리했다.
  검색·찜·클러스터·이동한 지도에서 초기 기본 화면의 캐시를 덮어쓰지 않는다.
  전체 원본/사진의 완성 캐시로 저장하지 않는다. 초기 실제 원장 최대 144건만 별도로 보관한다.
- 인증 후 동일 계정/빌드/화면 크기/기본 범위/부모 검증이 맞는 캐시의 실제 목록·사진을 먼저 표시한다.
  인증 전 표시하지 않으며 준비 전 조작은 inert로 막는다. 초안/메모/실행 속성은 캐시 HTML에서 제거한다.
  최근 자료에는 최근 확인 목록임을 표시한다. API/HTML/인증·타계정 자료의 공용 캐시 범위를 넓히지 않았다.
- 초기 Kakao SDK의 기본 중심 반올림 22 microdegrees를 실기에서 확인했다.
  기본 7레벨의 0.0001도 이내 반올림만 허용하며 사용자 지도 이동·필터·찜·클러스터 선택은 선표시 범위에서 제외한다.
- 보호된 Object.freeze 캐시 API를 덮어쓰던 초기화 오류를 제거했다.
  persisted=true, queued=false, 정확히 일치하는 원장 ID의 정식 저장 완료 이벤트로 연결한다.
- 저장 이벤트는 먼저 계정별 세대를 바꿔 늦은 응답을 차단한다. 원장 ID별 성공 영수증으로 초기 캐시를 보완한다.
  연속 조건 수정·메모 추가의 영수증을 같은 ID에만 합쳐 보존한다. 이전 원문 사진은 그대로 보존한다.
  기존 가격의 HTML은 재생하지 않는다. 이 로컬 보완 자료는 per-property 상태이며 최신 전체 목록으로 인증하지 않는다.
  실제 서버의 새 검증 자료가 도착하면 교체한다. 다른 탭/계정/구조 변경과 경합하면 잘못된 캐시 승격을 거부한다.
- 캐시에서 파생한 지번 검색도 작은 revision 확인 전에는 최신이라고 표시하지 않는다.
- 시장·조건을 바꾸는 동안 이전 시장의 카드·건수를 새 결과처럼 보여주지 않는다.
  새 범위의 지연/실패는 그 범위의 상태로 표시하며 다른 시장의 원장이 있다는 이유로 오류를 숨기지 않는다.
- 화면 크기/보이는 영역이 달라진 캐시는 필요한 원장 점조회만 보충한다.
  이미 다른 화면에서 더 최신으로 읽은 원장과 검증값이 다르면 이전 캐시로 덮어쓰지 않는다.
- 느린 HTML 전달은 실제 인증 검증 완료 시각을 새 시각으로 바꾸지 않는다. 만료된 탐색 증명은 기존 세션 확인으로 돌아간다.
- 변경 없는 자동 갱신은 카드·선택 원장·사진 DOM·메모 IME와 커서를 교체하지 않는다.

검증
- pnpm run check: lint/typecheck/전체 Node/PC·모바일 원칙/공개·비공개 Worker dry-run.
  전체 검사 Node 2270/원칙 296 통과 후 보완된 코어·시장 흐름을 재검수했다.
  최종 전체 Node 2272, 쿼리 PC·모바일 50, 캐시 코어 12, 실제 인증/브리지 7 통과.
- 쿼리 시작 브라우저 검사는 uncaught pageerror도 실패로 취급한다.
- 실제 공개 인증, 계정 불일치, 부모/자식/스코프/필드 검증, 오래된 시장 응답, 타 탭 저장 세대,
  빈 결과, 가상 목록의 먼 행, 찜 점조회 합치기, 102개 선택, 행번호 변경 시 ID/사진 유지,
  한국어 조합/커서, 실제 이미지 decode 후 교체를 검사했다.
- 최신 목록 응답을 고의로 지연시켜 저장 직후 새로고침한 PC·모바일에서 월세80/지하1층/연락처,
  메모 수정과 추가가 유지되고 다른 원장은 그대로인지 검증했다. 운영 매물에는 검수용 저장을 하지 않았다.
- 공개 배포 뒤 cf:verify는 양 도메인의 HTML 전체 fingerprint 연결과 핵심 14자산의 실제 바이트를 확인한다(30응답).

실측과 완료 판정의 한계
- 운영 IAB에서 선화동192-3: 당근 1/9→2/9(960px), 네이버 1/16→2/16(1200px),
  실제 src 교체/complete=true/추가 로딩=false/data-photo-ready-ms=0을 확인했다.
- 같은 IAB에서 첫 실제 목록 1.413~2.861초, 선표시 2.373초/실제 목록 2.693초도 측정했다.
  인증·HTML 수신 이후 선표시는 약180ms였다. 유리한 표본만으로 개선율이나 0초를 주장하지 않는다.
- 한 요청은 HTML 첫 바이트22.766초/수신 종료23.713초, 목록 조회10.765초였다.
  페이지 안의 목록 연산과 HTML/서버/통신 대기를 분리한 관측이지 그 원인을 특정 사업자 장애로 확정한 것은 아니다.
- 새 형식으로 옮기는 첫 접속 표본은 실제 목록9.092초/코드 준비2.852초/조회3.501초였다.
  이 값도 기록하며 캐시 없는 첫 접속까지 무대기라고 주장하지 않는다.
- 최종 배포 후 첫 reload는 실제 목록4.277초/조회4.740초, 다음 reload는 선표시2.421초/실제 목록2.734초였다.
  두 번째 인증준비2.261초/HTML수신0.544초/조회7.508초도 분리 기록했다. 목록9126개·36카드와 첫4사진 decode 확인.
  시장 전환 건물10421개/토지912개와 각18카드 verified를 확인했다. 찜4개 중 미확인1개는 삭제하지 않고 유지했다.
  이는 전체 지역·시점이 다른 화면의 수치이며 과거 좁은 지도 건수와 직접 비교할 수 없다.
- 따라서 조회 분리 구현과 운영 적용은 완료 범위지만 모든 새로고침/새 기기/통신 장애까지 무대기 달성으로 보고하지 않는다.
  실제 사용자 Edge 프로필·폰 하드웨어와 수집 동시 장시간 관찰은 이 IAB/Edge 가상 기기 검사와 구분한다.
  v138 일반 추가 메모의 모든 서버 동시 경합을 해결한 작업이라고도 보고하지 않는다.
