사용자 승인: 매매 수집이 계속 완료되지 않는 원인 확인 및 기존 승인 범위의 수정·검수·배포.

확인한 운영 증거
- Cloudflare 공식 Workers GraphQL 실행 통계에서 exceededMemory가 반복됨. 19:31:30, 20:02:30, 20:05:31 KST에도 해당 오류가 있고, 대덕구·중구·동구의 미확인 저장 접수 시각과 근접함. 과거 요청별 stack/URL은 조회 권한 부족으로 확보하지 못했으므로 모든 개별 실패의 동일 원인까지 확정하지 않음.
- 앞선 속도·receipt 수정으로도 런타임 강제 종료 자체를 막지 못했음. received 합계와 실행기의 unchanged 포함 processed는 서로 다른 수치이므로 혼용하지 않음.
- 보관된 운영 CSV 스냅샷은52,751,005 bytes. 기존 cold CSV 경로는 전체 SQL 원문/배열/CSV/UTF-8 해시/응답을 겹쳐 생성하고 module sheetCache에 큰 body를 유지했음. 전체 source 목록도 원문들을 모두 유지한 뒤 compact 변환함. 같은 isolate의 다른 요청/정기 작업에 메모리 압박을 줄 수 있는 구현임.
- 별도 복구 결함: 클라이언트가 pending descriptor를 보관했지만 POST가 claim 전에 끊기면 서버에는 요청 자체가 없고, 기존 status missing 경로는 계속 기다림. 이는 코드/경합 시험에서 검증한 경로이며 현재 PC의 로컬 pending 내용을 직접 읽어 해당 사례라고 단정하지 않음.

변경
1. 실제 R2 binding의 CSV cold build를500행씩 변환→고정5 MiB multipart 조각→complete 후 R2 stream으로 변경. 전체 CSV/해시/응답 복사 및 큰 module body 보관 제거. 중간 실패는 abort, 기존 검증 cache 유지. 인증 전 조회 없음, force fresh/304/압축/revision 의미 보존.
2. unified 원문은 기존4000행 keyset page별로 변환. 원문은 버리고 정확한 source identity proof만 보관, 마지막 parent inventory/count/version과 대조. manual history는 각 source page 이후 해당 parent 범위로 읽음. 편집 경합 검사는 유지. JSON도 작은 그룹별 multipart 직렬화→stream, 같은 env/key cold build만 공유. 광고/사진/검색 ID/대표 조건/공개 제외 기준 유지.
3. POST mutationStatus에서 정확한 Naver batch ID가 missing이고 실제 소유 Naver 세션이 running일 때만 INSERT...ON CONFLICT DO NOTHING으로 실패 fence 생성. 정상 write claim과 원자 경합하며 fence가 이긴 ID의 지연 POST는 쓰기를 시작할 수 없음. claim이 이미 존재하면 절대 변경/해제하지 않음. 결과는 ok:false/naver_request_not_accepted이며 전체목록 재대조를 요구. 구버전6.0.14도 확정 실패를 받아 로컬 pending을 지우고 다음 자동 시도 가능. 성공/수집완료로 가장하지 않음. GET 상태조회는 계속 읽기 전용. 운영 원본·매물·사진·개인 기록·존재검증 기준 미변경.
